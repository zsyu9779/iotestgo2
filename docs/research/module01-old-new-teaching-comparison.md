**调研对象**

- 新项目：`/Users/zhangshiyu/iotestgo2/module01_basics`
- 老项目：`/Users/zhangshiyu/iotestgo`
- 调研目标：在保留新项目课程节奏、实验和验收体系的前提下，找出老项目中没有被完整迁移的 Go 语言语义、反例和讲解方法。

## 一、结论先行

新项目的课程工程能力明显更强：它有清晰的 Block、时间盒、Starter/Solution、Quiz、讲师 Runbook、Task Manager 作业和 Bonus 入口。老项目的内容广度和“语言细节敏感度”更强：它不是按照教学产品设计的，但大量代码会故意把相邻语法放在一起，通过输出、编译错误、panic 和“看起来应该一样但结果不同”的例子，让学生理解 Go 的真实语义。

目前最大的迁移损失不是“少了多少 API”，而是下面这类教学精髓被压扁成了结论：

> 旧项目经常先制造一个可观察的反差，再解释规则；新项目目前更多是先写出正确代码，再用文字总结规则。

用户补充的 `const` 示例就是典型案例。它同时展示：

1. `iota` 是 ConstSpec 的行号，从 `0` 开始，每行继续递增；
2. 省略表达式时，复用上一行的完整表达式，而不是只复用 `iota`；
3. `consD = 250` 后的 `consE` 仍然是 `250`；
4. `consF = iota` 重新显式使用当前行号，因此得到 `5`；
5. 新的 `const (...)` 块会把 `iota` 重新置为 `0`。

这比“`iota` 可以生成连续数字”更接近学生工作中真正会遇到的坑。

### 核心判断

- 新项目缺的不是更多文件，而是“一个语义现象至少有一个可预测、可运行、可解释的对照实验”。
- 老项目多处把多个相关概念放在同一个 Demo 中，虽然不适合直接投影，但有利于发现语义之间的联系。
- 新项目此前把零值、String、控制流拆成多个 Demo，已经按要求收拢为 `02_vars_types` 和 `03_control_funcs`；后续也应继续按“讲解主题”合并，而不是按每个语义点单独建目录。

#### `iota` 推荐课堂实验

```go
const (
	consA = iota // 0
	consB        // 1：复用 = iota
	consC        // 2
	consD = 250  // 3：iota 仍然递增，但表达式改了
	consE        // 4：复用完整表达式 = 250
	consF = iota // 5：显式恢复使用 iota
	consG        // 6：复用 = iota
)

const (
	resetA = iota // 0：新的 const 块重新开始
	resetB        // 1
)
```

投影前先让学生写预测值，运行后再解释“行号”和“隐式复制”是两个不同维度。

### 4. Array、Slice、Map

旧项目证据：`/Users/zhangshiyu/iotestgo/mycollection/mycollection.go`、`mysort.go`

- `range` 的 value 是副本，按 index 才能修改原数组；

## 五、旧项目最值得迁移的“教学精髓”

### 精髓 1：先预测，再运行，再解释

旧项目的分隔线和连续输出虽然粗糙，却天然形成了实验节奏。新项目应把每个关键 Demo 设计成：

1. 代码只展示一个现象；
2. 讲师暂停，学生写出预测结果；
3. 程序输出结果；
4. 解释规则和生产建议；
5. 用一句话连接到 Lab。

`iota`、Slice 共享、defer 顺序、Map value 写回、值/指针接收者都适合这个模式。

### 精髓 2：对照相邻代码，而不是堆 API

最有效的对照对包括：

| 对照 | 学生要理解的规则 |
| --- | --- |
| `consD = 250` / `consE` / `consF = iota` | 隐式赋值复用完整表达式，iota 仍按行递增 |
| `for _, v := range arr { v = 99 }` / `arr[i] = 99` | range value 是副本，index 才能改原容器 |
| `map[K]Struct` / `map[K]*Struct` | Struct value 修改后要写回，指针 value 可直接改对象 |
| `defer fmt.Println(value)` / `defer func(){...value...}()` | 参数立即求值，闭包读取延迟到执行时 |
| 值接收者 / 指针接收者 | 接收者选择决定修改语义和方法集关系 |
| 普通 `switch` / `switch {}` | 前者匹配表达式值，后者按顺序匹配布尔条件 |

### 精髓 3：把“危险但值得知道”与“推荐写法”同时讲

旧项目保留了很多不应照抄的代码。新项目不应简单删除，而应改造成三段式标注：

- 规则：它为什么能运行；
- 风险：为什么生产代码通常不这么写；
- 替代：工作代码应该怎么写。

例如 `fallthrough`：讲语法和无条件进入下一个 case，但建议使用清晰的共享条件或函数。`goto`：说明能跳转，但通常用循环。`unsafe.Pointer`：说明其存在，但不作为普通指针教学的一部分。

### 精髓 4：错误示例必须能解释“为什么错”

老项目里有不少注释掉的错误代码。迁移时可以选择少量放入讲师材料：

- nil Map 写入会 panic；
- 对 nil pointer 解引用会 panic；
- 普通 Go 指针不能做指针算术；
- 未使用局部变量和 import 会导致编译失败；
- `:=` 只能在函数体内，并且左侧至少有一个新变量；
- `fallthrough` 不能放在最后一个 case。

错误代码不应放入正常 `go test ./...` 路径，最好用注释、讲师投影片段或单独的失败练习承载。

## 六、哪些内容不应该整体搬入新项目

老项目内容很丰富，但以下内容不应因为“完整”就进入 Module 01：

- 网络、HTTP/2/HTTP/3、WebSocket、TLS、UDP/TCP；它们需要独立的 I/O 和网络课程。
- cgo、系统调用、cgroup、namespace；它们属于系统编程专题。
- 反射全量 API；它应建立在 Interface、Struct 和 Pointer 之后，并以工程问题驱动。
- `unsafe.Pointer` 的数组指针运算；保留为警示材料，不作为能力目标。
- 大量 `strings` API 清单；新项目应该围绕文本统计或清洗任务选择 API。
- 旧项目的未格式化写法、忽略错误、`ioutil` 等时代性写法；只提取行为和概念，不复制风格。

## 七、建议的新 Module 01 教学主线

不增加新的碎片化目录，按现有 Demo 收拢：

### `01_hello`

只解决 `package main`、`import`、`func main`、运行方式和未使用代码约束。

### `02_vars_types`

按以下顺序组织：

1. `var`、短声明、类型推断；
2. `_` 和多变量声明；
3. 常量与编译期表达式；
4. 简单 `iota` 枚举；
5. 用户补充的隐式 ConstSpec / `iota` 边界实验；
6. 基本类型、显式转换、截断；
7. 零值、Struct 零值、nil Slice/nil Map；
8. 可选：`type Size int`、位运算、数字解析。

### `03_control_funcs`

按以下顺序组织：

1. if 初始化和作用域；
2. 三种 `for`；
3. `break` / `continue`；
4. 普通 switch、多值 case、默认不贯穿；
5. `switch {}` 和 switch 初始化；
6. `fallthrough`：真实运行、明确不推荐；
7. 多返回值、函数、匿名函数；
8. 与 Lab 的 `(value, error)` 契约连接。

### `05_strings_basics` 与 Block 2

核心讲 String 的不可变字节序列、UTF-8、byte/rune 和最常用清洗操作；将旧项目的 API 广度转化为一个文本清洗任务，而不是全部打印一遍。

### Block 2–4

保留现有 Demo 结构，逐个补“对照实验”而不是继续增加目录。特别是：

- Block 2：`copy`、Map value 写回、稳定展示无序 Map；
- Block 3：值/指针接收者、Embedding 不是继承、Interface/type switch；
- Block 4：defer 参数与闭包、error 类型、panic/recover 边界。

## 八、调研后的验收标准

后续补充内容满足以下条件才算真正完成迁移：

1. 学生运行前可以写出预期输出；
2. 输出能区分两个相似语法的行为；
3. README 解释规则，而不是只列 API 名称；
4. 讲师文档说明何时讲、何时跳过、为什么不推荐某写法；
5. 关键语义至少有一个 Exit Quiz 或 Lab 迁移问题；
6. 危险示例不会污染正常测试和作业路径；
7. 新增内容合并进现有主题 Demo，不为了每个语义点新建目录；
8. `go test ./module01_basics/...` 和课程验收命令保持通过。

## 九、最终判断

新项目不需要变成老项目的“更大复制品”。正确方向是：

> 用新项目的课程工程承载老项目的语义实验，用老项目的反差和输出补足新项目的语言深度。

其中最应优先落实的就是用户补充的 `const` / `iota` 实验。它体积很小，却能同时讲清楚隐式赋值、ConstSpec、行号递增和新块重置，是“少量代码、高教学密度”的典型样板。后续所有迁移都应以这个样板为标准，而不是以“旧项目有多少代码”作为完成度指标。
